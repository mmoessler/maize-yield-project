# Version control implementation

This document describes how version control is implemented in the standalone
`maize-yield-project` repository. It is an implementation reference for the
project rather than a complete introduction to Git and GitHub.

## Repository role

The repository is the version-controlled root of the project. It contains the
source code, report source, environment definitions, and documentation needed
to understand and reconstruct the analysis. Students clone this repository and
run Git commands from its root directory.

Git records changes to project files as commits. A remote repository makes
those commits available for backup and collaboration; it is not a substitute
for a local working copy.

## Clone and inspect the repository

Clone the project, enter its directory, and inspect its state:

```bash
git clone <course-repository-url> maize-yield-project
cd maize-yield-project

git status
git branch --show-current
git remote -v
git log --oneline --decorate -5
```

Replace `<course-repository-url>` with the HTTPS or SSH clone URL supplied for
the course. Use HTTPS unless an SSH key has already been configured for the Git
hosting service.

## Configure remotes for course work

Students who have their own copy of the repository should use two remotes:

- `origin` points to the student's repository and is the normal push target;
- `upstream` points to the course repository and provides course updates.

After cloning the course repository, configure this arrangement with:

```bash
git remote rename origin upstream
git remote add origin <student-repository-url>
git remote -v
git push -u origin main
```

`origin` and `upstream` are conventions, not special Git keywords. Confirm the
current branch with `git branch --show-current`; if it is not `main`, use the
reported branch name in the push command.

If students only need to read and run the original project, they can retain the
course repository as `origin` and omit the second remote. They will normally
not have permission to push to it.

## Tracked source and configuration

Git tracks the material needed to understand and reconstruct the project:

- R scripts and reusable functions;
- Quarto report source;
- README and implementation documentation;
- `renv.lock`, the `renv` bootstrap, and settings;
- Dockerfile and Docker build-context rules;
- project configuration and ignore rules;
- the communication figure retained for teaching and reference.

The repository does not treat every local artifact as source.

## Ignored generated and local files

`.gitignore` excludes:

- R and RStudio session state;
- `.env` secrets or local configuration;
- downloaded raw data, except the deliberately tracked teaching sample;
- processed data and fitted model objects;
- rendered Quarto HTML and support files;
- logs and partial downloads.

Inspect ignore decisions with:

```bash
git status --short
git check-ignore -v path/to/file
```

An ignored file is not automatically reproducible, safe, or disposable. The
workflow and documentation must still explain how to obtain or recreate it.

## Generated-output policy

| Artifact | Git policy | Reason |
| --- | --- | --- |
| R and Quarto source | Track | Primary project source |
| Environment definitions | Track | Required to recreate execution |
| Raw FAOSTAT download | Ignore | Large external source; acquired by script |
| Compact FAOSTAT teaching sample | Track | Supports offline and reliable course use |
| Processed tables and models | Ignore | Generated by scripts |
| Rendered report HTML | Ignore | Generated from source and outputs |
| Communication figure | Track | Visible example artifact used in the repository |
| Exploratory figures | Ignore | Recreated from the visualization script when needed |
| Credentials and `.env` | Ignore | Local and potentially sensitive |

If licensing, size, reliability, or teaching requirements change, revise this
policy deliberately and document the reason.

## Everyday workflow

Start by synchronizing the branch used for your work:

```bash
git status
git pull --no-rebase origin main
```

Only pull into a clean working tree. If the project uses a branch other than
`main`, substitute its name. After editing, review and commit a focused change:

```bash
git status --short
git diff
git add <path-to-changed-file>
git diff --staged
git commit -m "Describe the completed change"
git push origin main
```

Stage selected paths so that generated files, unrelated edits, and sensitive
information are not included accidentally. A commit should represent one
coherent change and its message should explain the outcome.

For work that should be reviewed before it enters `main`, create a branch:

```bash
git switch -c <short-branch-name>
git push -u origin <short-branch-name>
```

## Receive course updates

With the two-remote arrangement, inspect course changes before integrating
them:

```bash
git status
git fetch upstream
git log --oneline --graph --decorate --all
git merge upstream/main
git push origin main
```

Commit or safely set aside local work before merging. Merge conflicts are not
resolved correctly by choosing one side automatically: inspect the competing
changes, edit the affected files, test the result, and then commit the
resolution.

If the course repository is still named `origin` and there is no student
remote, update the local copy with `git pull --no-rebase origin main` instead.

## Re-create a working copy

To work on another computer, clone the student's repository and restore the
course remote if it is needed:

```bash
git clone <student-repository-url> maize-yield-project
cd maize-yield-project
git remote add upstream <course-repository-url>
git remote -v
```

Cloning restores tracked files and history. It does not restore ignored data,
generated outputs, credentials, or installed packages. Use the documented data
acquisition and reproducible-environment workflows to recreate those parts.

## Safety and review checks

Before committing or pushing, confirm that:

- no raw or processed data were staged unintentionally;
- no `.env`, token, password, private key, or private endpoint is present;
- scripts use project-relative paths;
- `renv.lock` changes are intentional and correspond to package changes;
- generated artifacts follow the documented policy;
- `git diff --staged` contains only the intended change;
- the current branch and push remote are the intended targets.

Git records project history. It does not validate scientific assumptions, data
licenses, private information, or whether generated outputs are correct.
